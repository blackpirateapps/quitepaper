You are working on the Flutter application **Quiet Paper**, an offline-first, privacy-focused notes application inspired by Bear Notes.

The repository already contains a mature Markdown editing system, a semantic WYSIWYG editor, E2EE sync, local SQLite persistence, Markdown import/export, backups, frontmatter support, tags, note links, tables, images, code blocks, checklists, read-only mode, note password protection, autosave, search, and responsive phone/tablet layouts.

Your task is to **replace the existing visual/WYSIWYG editing implementation with a new production-grade rich-text editor architecture**.

This is not a styling refresh.

This is an editor architecture replacement.

The goal is to make the Visual editor feel like a native, calm, continuous writing surface similar in interaction quality to Bear Notes while retaining Quiet Paper’s existing Markdown interoperability, local persistence, encrypted sync, backups, imports, exports, and note features.

The most important architectural rule is:

> **Markdown must NOT be the live editing representation of Visual mode.**

Visual mode must directly edit a rich document model.

Markdown mode must directly edit Markdown.

Markdown becomes an interchange/serialization format at mode boundaries and persistence/sync/export boundaries.

Do not recreate the existing “visual editor over Markdown source” architecture under different names.

---

# 1. Existing product constraints that must remain intact

Quiet Paper currently has these product principles:

* Content-first writing experience.
* Warm editorial aesthetic.
* Borderless document-style title and writing canvas.
* Fast offline-first local persistence using Drift/SQLite.
* Client-side encryption using Argon2id and XChaCha20-Poly1305.
* Zero plaintext note content sent to the backend.
* Markdown interoperability.
* Invisible autosave.
* Responsive phone/tablet layouts.
* Native-feeling keyboard, selection, focus, copy, paste, undo and redo behavior.
* Existing note-level security, read-only mode, search, tags, note links, tables, images, code blocks, frontmatter, import/export and backup functionality.

The existing handoff explicitly describes the product as a calm Bear-inspired writing experience and calls for a restrained app bar, 30sp title, spacious body typography, automatic focus, autosave, and a distraction-free editing loop. Preserve those goals.

Do not weaken security, sync, backups, or Markdown compatibility to simplify the editor.

---

# 2. The architectural change

The current system conceptually works like this:

```text
Markdown
   ↓
semantic parser
   ↓
semantic blocks/runs
   ↓
visual editor
   ↓
map selection back to Markdown
   ↓
mutate Markdown
   ↓
reparse
```

Do NOT continue this design.

Replace it with:

```text
                       Note Editor Session
                              │
                 ┌────────────┴────────────┐
                 │                         │
                 ▼                         ▼
          Visual Editing             Markdown Editing
                 │                         │
                 ▼                         ▼
          RichDocument                Markdown string
                 │                         │
                 └────────────┬────────────┘
                              │
                    Explicit conversion
                              │
                    Markdown serializer
                    Markdown parser
```

There must be a clear distinction between:

1. **RichDocument** — the live editing representation in Visual mode.
2. **Markdown text** — the live editing representation in Markdown mode.
3. **Persisted note format** — initially continue using the existing Markdown-backed SQLite schema so there is no unnecessary database migration.
4. **Cloud sync/export/backup format** — continue using Markdown as the interchange representation.

Do not persist a second rich-text database representation yet.

The first production goal is to validate whether the new rich-text editor feels excellent.

# 3. Source-of-truth rules

Implement these rules exactly.

## Visual mode

When Visual mode is active:

```text
RichDocument = authoritative editing state
Markdown = serialized interchange state
```

Typing, deleting, selecting, bolding, italicizing, creating headings, creating lists, checking checkboxes, inserting links, etc. must modify the RichDocument directly.

Do NOT modify Markdown on every keystroke.

Do NOT parse Markdown on every keystroke.

Do NOT map visual selection offsets through Markdown source ranges.

Do NOT expose hidden Markdown delimiter offsets to the editing controller.

Do NOT use source Markdown as the cursor coordinate system.

## Markdown mode

When Markdown mode is active:

```text
Markdown string = authoritative editing state
```

The user gets a normal Markdown text editor.

Typing:

```markdown
# Hello

This is **important**.
```

must behave like a normal text editor.

No rich-text mutation layer should participate in ordinary Markdown typing.

## Switching Visual → Markdown

On switch:

```text
RichDocument
    ↓
MarkdownSerializer
    ↓
Markdown text
    ↓
Markdown editing controller
```

Perform the serialization once during the mode transition.

Carry the user's source-equivalent caret/selection into Markdown mode when practical and safe.

## Switching Markdown → Visual

On switch:

```text
Markdown text
    ↓
RichDocumentParser
    ↓
RichDocument
    ↓
Visual editor
```

Parse once.

Carry the source caret/selection into the corresponding rich-text position where possible.

Do not attempt to continuously synchronize both representations while typing.

# 4. RichDocument architecture

Create a new editor domain model specifically for rich-text editing.

Do not simply reuse the existing `SemanticDocument` as the editing model.

The existing semantic architecture was designed around Markdown source ranges, hidden Markdown delimiters, source-to-visual mapping and semantic mutations. That is precisely the coupling this project is trying to remove.

Create a new clean model.

Recommended structure:

```text
RichDocument
 ├── blocks[]
 │
 ├── metadata/session information where appropriate
 │
 └── document-level helpers
```

Blocks should represent editing concepts rather than Markdown syntax.

At minimum support:

```text
Paragraph
Heading
BulletedListItem
OrderedListItem
ChecklistItem
Quote
CodeBlock
HorizontalRule
Image
Table
```

Inline content should be represented as text plus formatting attributes/runs.

At minimum support:

```text
bold
italic
strikethrough
highlight
inlineCode
link
noteLink
tag
```

The RichDocument must not contain Markdown delimiter characters merely to make serialization easier.

For example, bold text should conceptually be:

```text
"hello"
bold = true
```

not:

```text
"**hello**"
```

A heading should contain:

```text
type = heading
level = 1
text = "Hello"
```

not:

```text
"# Hello"
```

A checklist should contain:

```text
type = checklist
checked = false
text = "Buy milk"
```

not:

```text
"- [ ] Buy milk"
```

The model is allowed to have internal IDs for blocks/runs for stable rendering and editing, but those IDs must be editor-local and must not become persisted document syntax.

# 5. Editing model requirements

The editor must behave like a single continuous document.

The user must NOT feel that they are editing separate Flutter widgets called:

```text
HeadingBlock
ParagraphBlock
ChecklistBlock
QuoteBlock
...
```

Those are implementation concepts only.

The interaction model must be:

> “I am editing one note.”

Prefer one coherent text-selection model over independent block selections whenever technically possible.

Avoid architecture where every block has its own independent:

* TextEditingController
* FocusNode
* TextField
* selection state
* keyboard connection
* undo history

unless there is a compelling technical reason for a specific non-text surface such as a table cell.

The current editor has had repeated bugs around block focus, block IDs, selection projection, focus retention and programmatic selection synchronization. Do not carry that complexity into the new implementation.

* Select All.
* Copy.
* Cut.
* Paste.
* Delete.
* Backspace.
* Forward delete.
* Selection spanning formatted/unformatted text.
* Selection spanning multiple paragraphs.
* Selection spanning different block types where supported.
* Selection before/after links.
* Selection inside code.
* Selection inside tables.
* Selection around checklist text.
* Selection after inserting an image.
* Selection around a divider.
* Selection after formatting operations.
* Selection after undo.
* Selection after redo.
* Selection after mode switching.
* Selection after external note updates.

These interactions must never unexpectedly dismiss the keyboard:

* Typing text.
* Pressing Enter.
* Changing paragraph to heading.
* Changing heading level.
* Applying bold.
* Applying italic.
* Applying strike.
* Applying checklist.
* Applying list formatting.
* Applying quote.
* Inserting a link.
* Inserting a note link.
* Inserting a tag.
* Checking a checkbox.
* Switching between adjacent blocks.
* Typing at the beginning or end of a block.
* Undo.
* Redo.
* Opening or dismissing contextual formatting UI.

Do not rebuild the editing surface in a way that causes Flutter to dispose and recreate the active text editing state unnecessarily.

Do not rely on focus-node tricks to compensate for an unstable editor hierarchy.

# 8. Rich-text mutations

Formatting operations must operate directly on the rich document.

Examples:

Bold:

```text
selection
  ↓
apply attribute bold=true
```

Italic:

```text
selection
  ↓
apply attribute italic=true
```

Heading:

```text
current block
  ↓
set block type = heading
set heading level = requested level
```

Checklist:

```text
current block
  ↓
set type = checklist
set checked = false
```

Do not insert Markdown delimiter characters into the RichDocument.

Formatting must be composable.

The following must all work:

```text
bold + italic
bold + strike
italic + strike
bold + italic + strike
highlight + bold
inline code inside bold where semantically valid
link + bold
```

Avoid separate mutually-exclusive run classes if doing so makes combinations fragile.

A clean attribute-set model is preferred over a proliferation of special-case subclasses.

# 9. Typing continuity

Typing must feel completely natural.

Example:

User types:

```text
hello
```

then selects it and presses Bold.

After formatting, the user should simply continue typing.

If the cursor remains at the end of the bold range, continuing to type should produce predictable formatting behavior.

Formatting should behave similarly to a conventional rich-text editor:

* Applying Bold to a selection formats the selection.
* Applying Bold with a collapsed caret establishes an insertion formatting state.
* Turning Bold off ends that formatting state.
* Typing spaces must not cause formatting state corruption.
* Enter must have sensible style inheritance rules.
* New paragraphs should inherit only the formatting/block attributes that are appropriate.
* Empty formatting spans must not accumulate indefinitely.

Build a deterministic model for typing attributes instead of manipulating synthetic Markdown delimiters.

---

# 10. Enter behavior

Enter is one of the most important interactions.

Implement predictable behavior for:

* Paragraph → Paragraph.
* Heading → Paragraph where appropriate.
* Heading → same/lower semantic style according to normal editor conventions.
* Checklist → new checklist item.
* Completed checklist → new unchecked checklist item.
* Empty checklist → exit checklist.
* Bullet list → continuation item.
* Empty bullet → exit list.
* Ordered list → next number.
* Empty ordered item → exit list.
* Quote → continuation quote.
* Empty quote → exit quote.
* Code block → newline inside code.
* Divider → create editable paragraph below.
* Enter with active selection → replace the selection and continue from the resulting caret.
* Multiline paste → insert content without being mistaken for repeated Enter presses.

Do not hard-code these behaviors through Markdown string rewriting.

They are RichDocument mutations.

---

# 11. Backspace behavior

Backspace must feel like a native editor.

At the start of a block:

* Merge with previous compatible text block where appropriate.
* Convert an empty heading to paragraph where appropriate.
* Remove empty list/checklist/quote structure when appropriate.
* Handle divider deletion naturally.
* Do not accidentally delete unrelated metadata/frontmatter.
* Preserve inline formatting when merging.
* Preserve undo semantics.

Do not use raw source offsets as the primary editing mechanism.

---

# 12. Undo/redo

Implement a coherent editor-level undo/redo system.

A single user-visible action should normally correspond to one undo step.

Examples:

* Bold selection → one undo step.
* Create checklist → one undo step.
* Insert link → one undo step.
* Insert image → one undo step.
* Type a continuous burst of characters → natural text-editor undo behavior.
* Insert table → one coherent undo action where practical.
* Check a checkbox → one undo step.
* Mode switching itself should not generate meaningless user-visible undo history.

Do not generate enormous undo histories because of internal conversion or rebuild operations.

Undo must work independently of Markdown serialization.

# 13. Markdown serializer

Create a dedicated production-grade serializer:

```text
RichDocument → Markdown
```

It must handle all supported document structures.

Important:

The serializer is responsible for Markdown correctness.

The RichDocument is responsible for editing correctness.

Do not leak serializer concerns back into the editor controller.

Support the existing Markdown capabilities that Quiet Paper already supports, including:

* Headings.
* Paragraphs.
* Bold.
* Italic.
* Bold + italic combinations.
* Strike.
* Highlight.
* Inline code.
* Code blocks and language identifiers.
* Unordered lists.
* Ordered lists.
* Checklists.
* Nested lists where currently supported.
* Quotes.
* Horizontal rules.
* Links.
* Note links.
* Tags.
* Images.
* Tables.
* Frontmatter-preserving document assembly.

Use deterministic serialization.

Equivalent RichDocument states should serialize consistently rather than producing wildly different Markdown depending on editing history.

Do not serialize internal editor IDs.

Do not serialize temporary UI state.

# 14. Markdown parser

Create a dedicated parser:

```text
Markdown → RichDocument
```

This parser is for entering Visual mode and for loading Markdown into the visual model.

It should be independent from the RichDocument editing logic.

Do not make the RichDocument dependent on source ranges.

Do not make the editor selection system dependent on Markdown offsets.

The parser must preserve semantic content accurately.

When Markdown contains:

```markdown
**hello**
```

the parser should produce a rich run with bold formatting.

When it contains:

```markdown
# Hello
```

the parser should produce a Heading(level: 1).

When it contains:

```markdown
- [ ] Buy milk
```

the parser should produce a ChecklistItem(checked: false).

Do not introduce hidden syntax characters into the RichDocument merely because the input contained them.

* Tags.
* Checklist state.
* List structure.
* Code language.

* Image references.

# 16. Frontmatter

Keep the existing robust frontmatter system.

Frontmatter is metadata, not ordinary rich-text body content.

In Visual mode:

* Do not expose raw YAML to the writing canvas.
* Do not put YAML delimiters into RichDocument.
* Preserve unknown keys.
* Preserve comments.
* Preserve unrecognized attributes.
* Preserve original frontmatter formatting where the existing helper guarantees it.
* Continue supporting title synchronization.
* Continue supporting Author, Created, Source, Description, Tags and existing recognized metadata.
* Keep the current property editing UI or refine it to fit the new editor aesthetic.

When the user edits frontmatter in the dedicated metadata UI, update the canonical Markdown safely using the existing surgical frontmatter infrastructure.

When Markdown mode is selected, the full Markdown including frontmatter remains directly editable.

A malformed frontmatter block must never be silently destroyed.

# 17. Title handling

# 18. Checklists

Checklists must be true editor behavior.

Visual mode should render:

```text

```


The underlying RichDocument stores:

```text

```

not:

```text

```

Markdown serialization is responsible for converting the state to the correct Markdown syntax.

Preserve the existing Phosphor icon language used by Quiet Paper.

# 27. Autosave and persistence

The database should initially remain Markdown-backed.

When Visual mode is active:

```text
RichDocument
   ↓
debounced serializer
   ↓
Markdown
   ↓
existing note persistence
```

Do NOT serialize on every keystroke if it is unnecessary.

Use a sensible debounce and preserve the existing Quiet Paper autosave behavior.

Also flush on:

* focus change where appropriate
* app lifecycle changes
* editor disposal
* note navigation
* mode switch

Do not lose edits if the user immediately backgrounds the app.

Do not save an intermediate malformed Markdown state merely because a visual edit is in progress.

The RichDocument must remain the active editing state until serialization succeeds.

If serialization fails:

* do not silently discard the RichDocument
* do not overwrite the previous valid Markdown
* surface a recoverable error
* keep the editor usable
* log diagnostic information in development/debug builds

# 28. Performance

Performance is P0.

The current visual editor previously required incremental parsing, block virtualization, targeted rebuilds and large-document safeguards because full-document parsing and many live block widgets became expensive.

The new architecture should eliminate the need for Markdown reparsing during normal Visual typing.

Requirements:

* Typing in a paragraph should not parse the whole Markdown document.
* Inline formatting should not parse the whole Markdown document.
* Applying Bold should not reconstruct Markdown.
* Selection changes should not trigger whole-document serialization.
* Caret movement should not trigger a whole-document rebuild.
* Autosave serialization should be debounced.
* Large documents must remain responsive.
* Avoid rebuilding unaffected document regions.
* Do not instantiate unnecessary text-editing state for every block if the architecture allows a more efficient unified surface.
* Avoid O(N) listener fan-out per keystroke.

Create performance tests for:

* 1,000 paragraphs.
* 5,000 paragraphs.
* Large code blocks.
* Long checklist documents.
* Mixed-format long notes.

The target is that ordinary typing remains responsive and does not exhibit visible stutter caused by document conversion.

# 34. Failure handling

Conversion must be defensive.

Visual parsing errors:

* Do not destroy the Markdown.
* Do not silently produce an empty document.
* Fall back safely to Markdown mode when necessary.
* Explain the fallback clearly and calmly.

Serialization errors:

* Keep RichDocument alive.
* Do not overwrite last-known-good Markdown.
* Log actionable diagnostics.
* Allow the user to switch to Markdown mode and recover.

Unsupported Markdown:

* Preserve it.
* Never silently delete it.
* Where visual editing cannot safely represent it, render it as an explicitly unsupported/raw region or use an intentional Markdown fallback.

Never “best effort” destructively rewrite content.

Data preservation outranks visual prettiness.

Create a clean editor architecture.

Do not create giant God classes.

Keep:

* Visual typing does not parse Markdown.

# 40. Critical engineering instruction

Do not approach this task as:

> “Refactor the existing VisualDocumentEditor.”

Approach it as:

> **“Design and implement a new rich-text editor that happens to serialize to Markdown.”**

The distinction is critical.

The old editor's architectural problem is not simply bad selection restoration or insufficient optimization.

The deeper problem is that the user is editing a visual projection of another representation.

The new editor should instead make the rich document representation the actual editing representation.

Markdown should be treated as:

* import format
* export format
* sync interchange format
* backup/interchange format
* persistence format for the current experimental rollout

It should not be the live cursor/selection/mutation substrate of Visual mode.

---

# 41. Do not sacrifice the existing Quiet Paper character

The final editor should feel calm, warm and restrained.

Use typography, spacing and subtle separators to create hierarchy.

Do not solve complexity with more UI.

Do not add a permanent toolbar just because the new architecture supports more formatting.

Do not make the editor look like a generic rich-text component library.

The ideal result is:

```text
←                                           ⋯

My Weekend in Darjeeling
September 16 · 2 tags


We left early Saturday morning and drove
toward the hills.

The weather was surprisingly clear.

Things I want to remember

☐ Visit the tea gardens
☑ Find that little café again
☐ Book the train


A good note should disappear into your thinking.
```

The user should primarily see:

**paper, typography, content, cursor.**

Not:

**blocks, syntax, widgets, controls and implementation details.**

# 42. Development workflow

Before modifying code:

1. Inspect the current editor implementation and all editor dependencies.
2. Identify the minimum set of existing services that should be preserved.
3. Identify the old semantic-WYSIWYG-specific components that can eventually be removed.
4. Identify existing tests that encode desirable behavior.
5. Build the RichDocument domain model first.
6. Build parser and serializer.
7. Build mutations.
8. Build editor surface.
9. Integrate into `MarkdownEditor` and `EditorScreen`.
10. Add end-to-end tests.
11. Replace old Visual mode.
12. Remove obsolete visual-editor machinery.
13. Run full test suite.
14. Run static analysis.
15. Manually exercise representative notes with every supported block type.

Do not perform a speculative large-scale rewrite of unrelated parts of the application.

Do not touch cryptography, sync, backend security, or database schema unless strictly required.

Do not introduce unrelated UI changes while replacing the editor.
