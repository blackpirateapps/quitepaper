## A. Executive summary

**Release recommendation: BLOCK RELEASE.**

The feature has substantial working functionality, but the commit introduces two release-blocking regressions in the shared editor save lifecycle. Closing an editor during an overlapping save can discard its latest changes. Applying password protection during an ordinary save can return successfully without persisting encryption, and the plaintext note can subsequently be copied through the template service.

Eight confirmed findings are recorded: **two P0, one P1, five P2**. Nine correctness assertions fail because two independent attachment-encoding reproductions establish the same finding. Other confirmed problems affect attachment validation, mobile creation dismissal, valid CRLF frontmatter, notification error recovery and small-screen keyboard layout.

**355 repository tests passed** across selected template and regression suites. Static analysis passed before and after the audit. The final 14 additional audit probes produced **5 passes and 9 failures**. The two save-race probes pass against the actual pre-feature commit, supporting regression attribution. Passing repository tests therefore do not support release approval.

Migration and template backup transaction results were materially stronger: a populated database generated by the parent commit upgraded successfully, with all rows in its 16 application tables unchanged. Encrypted template backup round-trip, legacy payload compatibility, merge/replace behavior and injected restore rollback passed in the selected tests.

Confidence is **high** in the confirmed defects and tested persistence behavior, and **limited** for untested native-device behavior, full editor fidelity, release performance and process-interruption scenarios. This audit does not assert exhaustive correctness.

Sources inspected: `AGENTS.md`, `prompts/templates.md` (the original implementation specification), all requested handoff subsystem guides and index, the relevant latest-log entries including implementation log 334, `handoff/templates.md`, the implementing report `handoff/templates-report.md`, the implementation commit diff, template tests and relevant pre-existing regression tests. Actual source paths were traced from editor buffers through persistence, template storage, normal note creation, sync and backup restoration. No external web sources or implementing-agent claims were used as proof of behavior.

## C. Findings

### QPT-001

**Severity:** P0 — release blocker.

**Title:** Applying password protection during a save can succeed without encrypting the persisted note.

**Affected files:** `lib/features/editor/application/editor_provider.dart:96–106, 212–215, 263–290`; `lib/features/templates/application/template_service.dart:43–61`.

**Expected behavior:** A completed protection operation persists protected content; protected notes cannot become unprotected reusable templates. Existing security behavior must remain intact.

**Actual behavior:** While an ordinary save is blocked, `setPasswordProtection` sets the password and dirty flag, then receives the already-running save future. The old plaintext write completes; `_saveNow` clears dirty state because the Note object has not changed. No encrypted write runs. Database content remains plaintext even after the protection future completes.

**Evidence:** `audit-final.log`: `PROTECT: protected=false, dirty=false, activePassword=true`, followed by `PROTECT: service result=NoteTemplate`. Parent `baseline.log`: the same protection schedule persists ciphertext (`protected=true`). The probe uses real SQLite with a gated repository, not a mock database.

**Steps to reproduce:** Persist an ordinary note; update content and start a gated local save; before completion call `setPasswordProtection`; release the write; await both futures; re-read the DB. A direct `saveNoteAsTemplate` call with an ordinary flush then succeeds. The normal editor menu still checks activePassword, so this is not evidence that the same menu bypasses its own flag during that session. Reopening sees an ordinary plaintext note.

**Root cause:** The new `_pendingSave` coalesces state-changing requests without draining them. Dirty-state completion tracks only `state.note != noteToSave`, excluding password/hint/protection state.

**Impact:** Users can believe their writing is password-protected when storage remains unprotected. The service's persisted-content protection check cannot recognize this lost security transition. This concerns note-level protection; cloud note transport remains encrypted.

**Recommended fix:** Track a save revision that includes security state, capture immutable content/security inputs for each write, and serialize/drain through the requested revision. A successful protection call must await its own encrypted persistence. Preserve the service's eligibility recheck; do not solve this solely with UI hiding.

**Required regression test:** The exact in-flight protection race, plus protection removal, password change, lock and exit during queued saves, checking persisted encryption and subsequent service eligibility.

**Confidence:** High. Confirmed and baseline-compared.

### QPT-002

**Severity:** P0 — release blocker because the reproduced path silently loses current note edits.

**Title:** Exit cleanup can finish before the newest changes are persisted.

**Affected files:** `lib/features/editor/application/editor_provider.dart:214–215, 284–290, 300–309, 376–379`; callers in `lib/features/editor/presentation/editor_screen.dart:1879–1882, 1929–1932`.

**Expected behavior:** Existing exit/autosave behavior preserves the latest note state before the editor's save lifecycle ends.

**Actual behavior:** An exit request during an earlier save waits for only that earlier save. Newer text remains dirty and is scheduled for another 700 ms debounce. Disposing the notifier cancels that debounce. SQLite retains the older edit.

**Evidence:** `audit-final.log`: `EXIT: persisted=First edit, dirtyOnExit=true`; expected `Latest irreplaceable edit`. Parent `baseline.log` persists the latest edit and exits clean. The controlled repository keeps actual database writes ordered, avoiding an artificial reversed-write schedule.

**Steps to reproduce:** Open a persisted note; change body to A and start a local save; while it is in flight change body to B; call and await `handleExitCleanup`; release/finish the first write; dispose the editor; reopen. A is stored instead of B. Existing UI close/pop handlers do not await cleanup before route/editor teardown, further limiting recovery.

**Root cause:** `saveNow` now means “return the first active write,” while existing exit callers still expect “persist current state.” Only the template-specific flush attempts a second save; ordinary exit callers do not.

**Impact:** Applies to ordinary notes and existing users, even if they never use templates. History may sometimes contain a recoverable session snapshot, but this probe does not create one and history is not a guaranteed replacement for canonical persistence.

**Recommended fix:** Give all explicit save/exit operations an awaitable drain-to-revision contract; keep the notifier alive until persistence completes; await exit flushing before completing navigation. Handle write errors without discarding the dirty buffer. Reuse this contract for templates and protection.

**Required regression test:** The reproduced ordered in-flight save/second edit/exit/dispose sequence, followed by a real route-pop/provider-disposal widget test and lifecycle flush variants.

**Confidence:** High. Confirmed and baseline-compared.

### QPT-003

**Severity:** P1 — critical attachment-safety functionality defect.

**Title:** Encoded private links bypass attachment validation and enter independent notes.

**Affected files:** `lib/features/templates/application/template_content.dart:37–43, 47–73, 85–103, 114–118`.

**Expected behavior:** Private attachment/document references are refused in both Markdown and structured AST data, including legitimate alternate encodings. No broken ownership-dependent links are copied.

**Actual behavior:** An inline AST `linkUrl` encoded as `\u0071p:\u002f\u002fasset/private-id` decodes to `qp://asset/private-id` but passes validation, saves as a user template and instantiates a new note. Markdown `[private file](qp&#58;//asset/private-id)` also passes despite the Markdown parser producing a private `href`.

**Evidence:** Two failed audit assertions in `audit-final.log`. The AST test asserts the decoded inline link's exact URI before saving and records successful creation of a new note. The Markdown test independently asserts that the parsed anchor href is `qp://asset/private-id`.

**Steps to reproduce:** Persist valid RichDocument JSON with a paragraph inline link using JSON Unicode escapes; save and use it as a template. Alternatively validate the entity-encoded Markdown link above. No ImageBlock or AttachmentBlock is required for an inline resource link.

**Root cause:** Raw checking decodes only escaped slashes. The later AST loop examines block types and thumbnails, not decoded inline link attributes. The Markdown visitor checks images, not anchor/resource destinations.

**Impact:** New notes contain references whose resource lifecycle/ownership was not cloned. Deleting source-owned resources can leave reused templates/notes broken. The test confirms copying, not a demonstrated cross-account access or plaintext network leak.

**Recommended fix:** Traverse decoded canonical blocks, all inline/link metadata and table/content containers; inspect normalized destinations from the Markdown parse tree and existing resource utilities. Apply a shared resource policy after decoding, with explicit allowed ordinary/internal note links.

**Required regression test:** Valid fully identified AST paragraph links and Markdown entity/reference links for asset/document/attachment/file/content URIs; include positive ordinary web/note-link cases and verify refusal without source mutation.

**Confidence:** High. Confirmed through service + SQLite + instantiation for AST, and decoded Markdown parser output for the second form.

### QPT-004

**Severity:** P2.

**Title:** Text-only code examples are falsely refused as embedded media.

**Affected files:** `lib/features/templates/application/template_content.dart:37–43, 75–94`.

**Expected behavior:** Text-only documents and code fences are preserved; unsupported resource detection identifies actual embedded/referenced resources.

**Actual behavior:** A fenced text example containing `qp://asset/example` and literal `<img src="example">` throws the attachment refusal. Such code is not an embedded attachment. The same raw matching can affect escaped examples and technical prose.

**Evidence:** The unchanged “literal code examples are valid text-only templates” correctness assertion fails in `audit-final.log` with the exact unsupported-content message.

**Steps to reproduce:** Create a note with a text code fence containing the strings above and attempt Save as Template.

**Root cause:** Resource and HTML checks scan raw document bytes before/alongside parsing, without code/literal context.

**Impact:** Legitimate technical templates are blocked and users are told to make an already text-only note into a text-only copy.

**Recommended fix:** Make resource extraction aware of code spans/fences and escaped text. Inspect actual resource-bearing nodes, keeping genuine attachment rejection intact.

**Required regression test:** Fenced and inline code, escaped markup and ordinary prose containing resource-looking strings must save verbatim; equivalent live links/images must still fail.

**Confidence:** High.

### QPT-005

**Severity:** P2.

**Title:** Mobile sheet dragging dismisses an in-progress creation and loses its navigation result.

**Affected files:** `lib/features/templates/presentation/template_picker.dart:19–38`; `lib/features/templates/presentation/widgets/template_browser.dart:75–101, 120–123`; shared modal behavior in `lib/core/widgets/quiet_adaptive_modal.dart:56–57, 81–85`.

**Expected behavior:** Creation is protected from repeated activation/dismissal until its persistence result is handled, and a successfully created note opens normally.

**Actual behavior:** System Back is blocked, but a downward fling dismisses the sheet while creation is pending. After the operation completes, one note exists in SQLite, `created` is null, and the unmounted browser skips `onCreated`.

**Evidence:** `audit-final.log`: `DRAG: openBeforeCompletion=false, rows=1, returned=null` in a mobile widget test using the real picker and real persistence after release.

**Steps to reproduce:** Open picker on Android-style layout; select a template; hold creation with a deterministic gate; tap Use Template; fling the sheet downward; complete creation.

**Root cause:** The picker retains `enableDrag: true` from the adaptive modal. PopScope protects Back/maybePop behavior but does not prevent this sheet close path. Result handling belongs to the browser that was disposed.

**Impact:** A note is created without being opened or reported. Reopening and repeating can create unintended duplicates. The confirmed behavior is widget-emulated, not a physical Android replay.

**Recommended fix:** Tie modal dismissal/drag behavior to operation state, or keep a durable operation owner that can deliver the committed result after modal closure. Do not rely only on PopScope and disabled buttons. Apply the same audit to Save Template submission.

**Required regression test:** Drag, barrier tap, Escape and system Back during pending save/use, asserting either safe refusal of dismissal or reliable completion/result handling and exactly one note.

**Confidence:** High.

### QPT-006

**Severity:** P2.

**Title:** Templates with valid CRLF frontmatter can save successfully but fail on use.

**Affected files:** `lib/features/templates/application/template_content.dart:149–164`; existing helper `lib/features/editor/application/frontmatter_editor_helper.dart:49–50, 105–109, 355–368`.

**Expected behavior:** Supported YAML title normalization changes only the instantiated title, preserving unrelated metadata and valid source line endings.

**Actual behavior:** A note with CRLF frontmatter and `author` before `title` saves as a template; instantiation throws “The frontmatter title could not be updated safely.” No new note is inserted.

**Evidence:** Full save → instantiate service reproduction in `audit-final.log`, using `---\r\nauthor: Alice\r\ntitle: Old\r\ncustom: value\r\n---\r\nBody`.

**Steps to reproduce:** Persist that body as an ordinary note, save it as template “New title,” then use the template.

**Root cause:** The existing helper splits on `\r?\n` but advances source offsets by only one newline character. Later value ranges are wrong for CRLF. This helper defect pre-exists the template commit; the new template title-normalization path exposes it as a required-feature failure. It is not a newly introduced general YAML parser bug.

**Impact:** A valid Windows/imported document produces an unusable template. The post-normalization safety check prevents a partially corrupted note from being persisted.

**Recommended fix:** Calculate ranges using original newline widths/source offsets; preserve other bytes. Extend safe normalization to supported input variants without removing the final title-consistency guard.

**Required regression test:** Actual save/instantiate for LF and CRLF, title at multiple positions, comments, quoted names and unrelated custom fields; compare untouched metadata/body byte-for-byte.

**Confidence:** High.

### QPT-007

**Severity:** P2.

**Title:** Post-save notification exceptions report committed creation as failed and duplicate it on retry.

**Affected files:** `lib/features/templates/application/template_service.dart:100–102`; `lib/features/templates/application/template_providers.dart:17–19`; UI error handling in `lib/features/templates/presentation/widgets/template_browser.dart:82–99`.

**Expected behavior:** Once a valid note commits, notification/sync scheduling failures must not misrepresent the persistence outcome or make a retry create an extra note.

**Actual behavior:** If `onNoteCreated` throws, `instantiate` throws after saving the note. A second identical UI-style retry creates a second committed note and throws again.

**Evidence:** Injected callback failure in `audit-final.log`: `CALLBACK: rows after reported failure=1`; `CALLBACK: rows after retry=2`. Actual SQLite persistence runs before the injected failure.

**Steps to reproduce:** Supply an `onNoteCreated` callback that throws a StateError, call `instantiate`, catch the reported failure, retry, then inspect the note table.

**Root cause:** An unguarded ancillary callback is part of the creation success/failure contract after commit. Production callbacks read collection/sync providers, so initialization/disposal exceptions would cross the same boundary.

**Impact:** False failure UI and duplicate ordinary notes. The failure contract is confirmed by injection; an organic production provider-disposal trigger was not reproduced and is not claimed.

**Recommended fix:** Preserve and return the committed Note independently of ancillary refresh/sync failures; schedule/report those failures separately and retry notification, not creation. Where navigation can fail after commit, retain the existing note identity for recovery.

**Required regression test:** Inject refresh/sync callback and navigation failures after commit; retry must reopen/recover the existing note or explicitly start a new operation, never duplicate under a failed-operation retry.

**Confidence:** High for the confirmed error-path behavior; production trigger frequency is unmeasured.

### QPT-008

**Severity:** P2.

**Title:** Small-phone picker overflows when the keyboard is visible.

**Affected files:** `lib/features/templates/presentation/template_picker.dart:24–33`; `lib/features/templates/presentation/widgets/template_browser.dart:140–225, 226–285`.

**Expected behavior:** The picker remains usable in a constrained phone viewport with the keyboard visible; required controls remain reachable.

**Actual behavior:** At logical size 320×568, DPR 1 and bottom keyboard inset 300, Flutter reports a 34-pixel bottom RenderFlex overflow. Existing tests at 360×640 do not detect it.

**Evidence:** `audit-final.log`: `SMALL_PHONE: error=A RenderFlex overflowed by 34 pixels on the bottom.`

**Steps to reproduce:** Configure that viewport/inset, open the real Android-style picker with default text scale, and let its autofocus search field remain visible.

**Root cause:** Available height is reduced for keyboard/insets, while the browser keeps header, padded search and footer outside its sole flexible list. Their minimum combined height exceeds the remaining viewport.

**Impact:** Clipped/overflowed controls and effectively unusable list space on small phones or similarly constrained windows. Larger text can further constrain layout but was not measured here.

**Recommended fix:** Use constraints-aware scrollable/sliver composition or adapt chrome/search/footer sizing so all essential controls remain reachable; account consistently for modal and keyboard padding.

**Required regression test:** 320×568 with 300 inset, landscape, small resized desktop and large accessibility text scales, asserting no overflow and reachable search/rows/footer/use controls in both themes.

**Confidence:** High for the specified widget viewport; no native-device claim.

## D. Data integrity assessment

- **Source-note preservation:** Snapshot insertion itself reads the flushed source and writes only template tables. Normal source content, metadata and history remain unchanged in tested snapshots. Shared editor changes invalidate a broader safety claim: QPT-002 can discard pending source-note edits on exit.
- **Template immutability:** Canonical content is a String, template metadata/list snapshots are immutable and ordinary notes receive new identities. Creating two notes and editing one preserves the second, stored template and source in the tested rich fixture.
- **Editor content preservation:** Snapshot storage and instantiation preserve Markdown/AST bytes except deliberate title normalization on a new Markdown copy. Opening without editing preserves canonical JSON in all three modes. CRLF frontmatter is defective. Full cross-mode formatting fidelity is not proven.
- **Autosave races:** `flushForTemplate` correctly flushes Visual state and handles the tested overlapping text save. Failed flushing refuses a stale snapshot. The same protection does not cover ordinary exit or password-state changes; QPT-001/002 are release blockers.
- **Instantiation:** Real database failure during tag insertion rolls back the note and newly created tags. Fresh metadata/default state and independence are verified. Postcommit callback errors and modal closure still mishandle successful persistence.
- **Attachment safety:** Direct ordinary resource forms/images are refused, but encoded inline links are demonstrably accepted. No claim of safe unsupported-resource isolation is supportable until QPT-003 is fixed.

### Existing editor behavior distinguished from template regressions

The added cross-editor probe opens a Visual AST source, snapshots it, creates two notes, opens a copy in Markdown Source without rewriting it, opens it in Super Editor, inserts text, autosaves, closes and reopens it in Visual. It checks representative content sentinels, completed/nested tasks, code language, link targets and independent storage. It does not exercise every mode-selector click or all semantic attributes.

Its output includes `**Bold** and* italic*` where the original had `**Bold** and *italic*`. `baseline-conversion.log` reproduces the same change in the parent commit with an ordinary note and the existing RichDocument-to-Super serialization pipeline. This is a confirmed pre-existing conversion defect, not a new template finding. List serialization also normalizes markers/numbering in the observed workflow; full list-hierarchy equivalence was not asserted. Do not convert this probe's “pass” into a claim of lossless editing.

Ordinary Super Editor task/math and Visual selection/undo/table regression suites passed, but exhaustive Backspace/delete/caret/IME behavior on template-derived notes was not independently exercised. Markdown escaping, complete YAML dialect support and arbitrary AST metadata combinations remain broader coverage gaps.

## E. Database and backup assessment

**Migration:** Schema advances from 20 to 21; fresh creation includes both dedicated tables; upgrade creates only those two tables inside a transaction. No destructive migration of notes/tags/attachments/sync data appears in the feature diff. Generated Drift code is present and compiled successfully. Code generation was not rerun during a read-only audit.

**Actual upgrade verification:** A detached worktree at the parent commit generated a real version-20 DB with ordinary, pinned, archived, trashed and journal notes; nested tag hierarchy and assignments; sharing metadata; server revisions, dirty/synced timestamps; sync cursor and pending deletion; an attachment, a document and a history entry. The v21 application upgraded a copy and compared every row in all 16 baseline application tables. All matched. `PRAGMA foreign_key_check` returned no rows; `PRAGMA integrity_check` returned `ok`; a template insert succeeded afterward. Original v20 fixture is retained.

**Limits:** Older migration regression tests passed, but were not supplemented with populated fixtures for every historical release. No migration process kill, storage-exhaustion or multi-process-upgrade contention experiment was performed. There is no evidence here of destructive template migration behavior.

**Backups:** User templates/favorites are optional fields in BackupPayload v1. Built-in bodies are not database rows and are not exported. Password-encrypted backup strings restore snapshots/favorites and permit new ordinary note creation. Legacy sections omitted from a payload restore successfully. Explicit unencrypted export remains an existing user option and is not described as encrypted.

**Restore atomicity:** Template validation precedes destructive operations. Template changes and ordinary note changes share the restore transaction. Restored content still uses the validator with the encoded-resource weakness in QPT-003; transactional correctness does not establish content-policy correctness. The existing injected late note-insert failure rolls back template replacement. An additional favorite-insert trigger failure after replacement starts also preserves local template/favorites and the pre-existing ordinary note. Merge newer/tied timestamp cases pass; template keepBoth follows the same stable-ID upsert branch by inspection. The pre-existing attachment/document restore code performs filesystem writes outside SQLite's rollback capability; this audit did not establish full filesystem/crash atomicity or attribute that pre-existing design to templates.

**Vault deletion:** The established erase transaction deletes favorite and template rows; the corresponding test passes. Bundled definitions remain available. SQL deletion does not establish secure physical erasure of old SQLite pages/WAL or external backup files.

## F. Security assessment

**Zero-knowledge/cloud separation:** The feature adds no backend changes/endpoints or template HTTP client. Template tables have no dirty/revision sync fields. Sync still obtains ordinary dirty notes and encrypts NotePlaintext before creating payloads (`lib/core/sync/sync_engine.dart:210–241`). Local template/favorite operations do not create ordinary note/sync rows; resulting instantiated notes follow the established encrypted path. Selected existing sync tests passed. No live backend deployment or packet capture was performed.

**At rest:** NativeDatabase is ordinary SQLite. Template content, names, default tags and favorite associations are plaintext application data in that file; cloud E2EE does not encrypt them locally. OS/storage protection is separate. The documentation correctly acknowledges this limitation.

**Protected notes:** Persisted ciphertext is normally rejected in the service even when the original editor has been unlocked. However, QPT-001 loses a newly requested protection transition during an in-flight save and permits a subsequent direct plaintext template snapshot. Protection cannot be approved.

**Logging:** Template UI logging prints exception runtime types rather than bodies/keys; error text is mapped to safe messages. No new template network or body logging was found. This is source-path inspection, not an audit of every existing global logging facility.

**Resource boundary:** Encoded private resource references bypass the selected-document validator. This is a content ownership/lifecycle defect; cross-user exfiltration was not demonstrated.

## J. Final verdict

1. **Is the implementation functionally complete?** No. Main surfaces exist, but several required safety, recovery, frontmatter and responsive behaviors are defective.
2. **Is existing note data safe?** Not sufficiently. QPT-002 demonstrates silent latest-edit loss in an existing editor path; QPT-001 loses an intended protection transition.
3. **Are all three editor modes compatible?** Representative loading and an editing/reopen path work, with independent storage. Full fidelity is not established; an existing emphasis defect and incomplete semantic coverage remain.
4. **Are database migrations safe?** The tested real v20 → v21 upgrade is safe and preserves all application rows. Exhaustive historical/crash safety is not claimed.
5. **Are encrypted backups and restoration safe?** The template payload encryption and tested transactional restore/rollback paths pass. Whole-filesystem/process-interruption atomicity is not established.
6. **Is the feature genuinely offline-first?** Yes for tested local template persistence, favorites and ordinary local creation; no template-specific networking is required.
7. **Are privacy and protection boundaries preserved?** Cloud template separation remains intact. Note-level protection is not preserved under QPT-001. Local template data is plaintext SQLite.
8. **Are all critical error paths covered?** No. Existing coverage missed both save races, resource encodings, modal drag and postcommit notification failure.
9. **Are tests sufficient to support release?** No. 355 existing selected passes coexist with nine failed additional correctness assertions.
10. **Would I approve deployment to real users today?** No.

**BLOCK RELEASE. Exact unresolved release-blocking findings: QPT-001 (lost password protection), QPT-002 (lost latest edits), and QPT-003 (private-resource validation bypass).** QPT-004 through QPT-008 also require correction before treating Phase 1 as production-ready.
